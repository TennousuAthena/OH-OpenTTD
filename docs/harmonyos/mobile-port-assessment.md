# 鸿蒙平板与手机移植评估

评估日期：2026-10-03。对象是当前工作区，包括尚未提交的 PC 移植和性能优化成果。本次做代码审查、现有主机测试及实际触摸识别器复现；没有在平板或手机上安装、运行或做发布验收。

默认条件：用户仅用手指操作，没有键盘、鼠标或手写笔。连接外设是增强能力，不能作为完成游戏流程的前提。

## 结论

平板值得优先推进：现有 arm64 游戏核心、XComponent、GLES、音频、资源与存档基础可以复用，设备声明也已包含 `tablet`。主要工作是接通系统输入法、修正触屏语义并验证手指操作的完整游戏流程。

手机在共享上述基础后，还需要单独处理小屏工具栏、弹窗、列表和精确建造；当前未声明 `phone`。增加设备类型、把 PC 界面整体缩放，并不足以完成手机适配。

| 目标 | 可复用基础 | 当前缺口 | 建议顺序 |
| --- | --- | --- | --- |
| 平板 | arm64 核心；已有平板声明；点击和建造拖动；普通窗口尺寸变化；前后台暂停 | 系统软键盘与中文 IME；独立地图平移/缩放；多指结束与取消安全；触摸尺寸；无键鼠实机闭环 | 先做横屏触屏基线，再验证旋转与分屏 |
| 手机 | 同一游戏核心和平台桥；平板阶段形成的触屏语义与 IME | phone 声明及打包验证；短边空间；刘海/导航区；窄窗与键盘下弹窗；手指遮挡 | 在平板基线后做手机横屏原型，再逐窗适配 |

当前配置是 target API 26、compatible API 20，原生 ABI 为 `arm64-v8a` 和 `x86_64`。兼容声明与 PC 成功不能代替相应 OS/API 的平板、手机运行验证。旧版发布文档和技能中的平台版本快照不作为本次能力证明。

## 已有能力与证据边界

- `harmonyos/entry/src/main/module.json5:7` 与 `harmonyos/product.json5:10` 只有 `tablet`、`2in1`。
- `harmonyos/entry/src/main/cpp/napi_init.cpp:138` 的 native touch callback 调用实际引擎导出；`src/video/harmonyos_input.cpp:761` 将触点快照入队；游戏线程在 `harmonyos_v.cpp:570` 排空队列。继续沿用这个线程边界。
- `harmonyos_input.cpp:617` 每帧检查静止触点，长按不依赖手指必须移动。单击和左键建造拖动已存在；PC 真机证据见 `port-guide.md` 第 12 节。
- `napi_init.cpp:111` 与 `harmonyos_v.cpp:566` 已有 surface 尺寸变化链，可作为横屏、分屏适配基础；不能据此认定安全区、DPI 或键盘避让已经完成。
- `EntryAbility.ets:30` 和 `harmonyos_v.cpp:552` 已支持前后台/窗口可见性暂停、输入重置、音频暂停与恢复。进程被回收后的存档恢复仍需设计和验证。
- 上游已有游戏内屏幕键盘：`src/misc_gui.cpp:893` 可打开 OSK，默认是双击触发（`src/table/settings/gui_settings.ini:204`）。它按有限字符布局插入字符（`src/osk_gui.cpp:107,352`），不能代替鸿蒙拼音候选、中文组合输入。

以上源码路径和行号对应评估时工作区。运行基础、主机模型、实际识别器测试、移动端实机验证是不同层次的证据。

## 优先修复的问题

### 1. 系统软键盘和中文 IME 尚未接入页面

`XComponentPage.ets:21` 只构建游戏 surface，没有实际 TextInput 或系统输入法客户端。NAPI 已导出 `getTextInputState`、`setTextInput`、`textInputKey`（`napi_init.cpp:147`），但 ArkTS 页面没有消费者。`TextInputBridge.ets:24` 只提供 controller/helper；其注释描述的 overlay 没有实现，`classify():35` 也没有真正识别组合态。

引擎已发布编辑框位置、文本、会话和序列（`src/video/harmonyos_textinput.cpp:49`），并有回写入口。建议在页面接入真正的 ArkUI TextInput 或系统输入法客户端，完成：

- 单击游戏编辑框即打开系统键盘；根据实际编辑框的限制处理字符，而非统一套用旧 helper 的固定 512 字节/256 字符。
- 同步焦点、光标、选择区、删除、候选预览、提交和取消；检查 UTF-16 与 UTF-8 偏移、过期会话回调、双向更新循环。
- 输入框和确认按钮在键盘出现时保持可见；关闭键盘后恢复游戏焦点。使用系统键盘时避免同时打开上游 OSK。
- 用中文公司名、车辆名、存档名及聊天做端到端验证。`test-bridges.sh` 的模型 PASS 不代表这些链路已完成。

### 2. 地图平移与缩放共用滚轮，默认行为冲突

`GameTouchSink::onScroll` 与 `onZoom` 都调用 `DoWheel`（`harmonyos_input.cpp:375`）。默认 `gui.scrollwheel_scrolling = SWS_ZOOM_MAP`（`gui_settings.ini:395`）；游戏只在 `SWS_SCROLL_MAP` 下按二维滚轮平移地图（`window.cpp:2875`）。

因此从实际映射和游戏代码推导：默认双指上下拖动会进入缩放，横向拖动无法稳定作为地图平移；改成滚轮平移后，捏合也会进入同一路径。还没有移动端真机行为记录。

应给触屏增加分开的平移与缩放语义，在游戏线程按目标窗口/viewport 路由。地图平移、地图缩放和列表滚动不能依靠同一个全局滚轮选项区分。

### 3. 多指结束可退化为建造拖动或右键

实际识别器 `harmonyos_touch.cpp:52,118,149` 在两指变一指时保留剩余手指原来的起点和按下时间，恢复单指分类。

本次链接实际 `harmonyos_touch.cpp` 复现了：

| 序列 | 当前输出 | 应有行为 |
| --- | --- | --- |
| 两指平移 20 个输入坐标单位，先抬一指 | 剩余指未继续移动也立即发 `DRAG` | 结束双指导航；其余手指抬起前不启动建造 |
| 两指静止 520ms，先抬一指 | 立即发 `LONG_PRESS` 和右键 | 不把双指导航余留指识别为新长按 |
| 两指间距从 100 每帧增加 2，最终 140 | 20 次 `SCROLL(0,0)`，没有缩放 | 识别累计 40% 的捏合变化 |
| 单指长按后继续移动 30 | 没有 `onDrag` | 若产品采用长按拖图，应持续平移 |
| 取消后收到孤立 active 快照，再抬起 | 发 `TAP` 和左点击 | 取消后的余留事件不得触发点击/建造 |

这些是识别器输出的实测结果；它们到实际游戏建造的影响由 `GameTouchSink` 源码推导，未做移动端实机确认。`DRAG` 会在游戏侧发左键按下（`harmonyos_input.cpp:346`），所以前两类转换必须在进入建造前阻断。

建议保留原始 DOWN/MOVE/UP/CANCEL 阶段，明确一个完整触摸会话的所有权。双指结束、取消、后台、失焦或坐标变换后，余留手指先进入等待释放状态；只有新的真实 DOWN 才能启动新操作。建造中加入第二指时，还必须验证释放左键是否提交了未确认的建造，不能把一次 release 当作安全取消。

### 4. 捏合与移动阈值没有按意图累计、按密度适配

`harmonyos_touch.cpp:186` 只比较相邻两帧距离，差值大于 4 才判捏合；缓慢捏合会丢失累计变化。`GameTouchSink::onZoom` 对每次比例变化直接发一个滚轮事件，没有实现 `input-matrix.md` 描述的约 15% 累计缩放步长。

另外 `beginTouch(..., density)` 忽略 density（`harmonyos_touch.cpp:17`），识别时固定传入 1.0（`:129`）。名为 `tapThresholdVp` 的 8 被直接用于 native 输入坐标比较。应明确 native 坐标、surface 像素、游戏坐标及 ArkUI vp 的契约，再换算距离阈值；本次不根据名字假定各端坐标单位已经一致。

使用累计距离/比例、手势方向及稳定的 finger ID；缩放以双指中心为目标，避免一帧微抖动反复在平移和缩放间切换。不同密度、不同事件采样频率应得到接近的操作感受。

### 5. 长按右键不能同时承担地图拖动和帮助

长按目前是一次即时右键按下/释放（`harmonyos_input.cpp:358`），没有右键持续保持；识别器长按后的移动也不发 drag。这与 `input-matrix.md` 写的长按后右键拖动存在差距。

右键提示还受 `hover_delay_ms == 0` 限制（`window.cpp:781`），默认值是 250ms。不能把“长按模拟右键”直接视为完成无悬停帮助。建议为控件帮助和地图导航定义独立的触屏规则，并验证提示是否持续可读、是否遮挡操作位置。

### 6. 小屏需要布局和点击尺寸适配

实际驱动直接把 surface 尺寸用于 `_screen`（`harmonyos_v.cpp:490`）；自动 GUI 比例按 640×480 设计尺寸计算（`src/gfx.cpp:1793`），没有用设备密度校准手指目标。高像素分辨率并不证明物理按钮足够大。

上游已经有窄屏主工具栏的上下组切换（`src/toolbar_gui.cpp:1805`），应该复用并测量；它仍有每组最少 14 个按钮的设计，不能当成手机菜单已经完成。订单窗口等界面包含多个 124 基准宽度的并排控件（`src/order_gui.cpp:1659`）。简单放大 GUI 会进一步占用短边空间。

平板先保留主要游戏窗口，扩大关闭、确认、滚动等常用触点并改善建造提示。手机先做横屏原型，使用分组/折叠工具栏、可滚动面板或优先显示一个主要操作窗；逐窗处理订单、车辆购买、车站选择和保存对话框。以至少约 48vp 的常用触点作为原型设计目标，再用实机验证；这是本项目建议值，不是已满足的指标。

### 7. 方向、安全区、返回和后台恢复尚需明确

`EntryAbility.ets` 与 `XComponentPage.ets` 没有明确方向、安全区、键盘避让或 `onBackPress` 策略；native `KEYCODE_BACK` 当前走退出请求（`harmonyos_input.cpp:295`）。应让系统返回依次收起键盘、取消当前工具/关闭当前对话框，再进入游戏退出流程。

所有遮挡区、辅助按钮布局和游戏点击位置使用同一份可用区域与坐标变换。旋转、分屏、键盘出现后需重新布局窗口并取消或安全结束进行中的手势，避免坐标突变提交建造。后台恢复与系统回收分别验收；增加游戏线程上的可靠存档检查点/恢复策略，明确恢复提示和存档选择。

平台已有窗口旋转策略和窗口避让区接口可用于实现，具体行为按实际系统/API 验证。参考华为官方[窗口旋转说明](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/window-rotation)与[沉浸式窗口说明](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/immersive-window-feature)。本次也核对了安装 SDK 中 `setKeyboardAvoidMode`、`keyboardHeightChange`、`avoidAreaChange` 的声明。

## 建议的默认触屏交互

以下是待实现的产品方案，不能作为当前能力描述。

| 场景 | 手指操作 | 游戏语义 |
| --- | --- | --- |
| 按钮、地图对象 | 单击 | 选择/打开；选中建造工具时放置 |
| 普通地图浏览 | 单指拖动 | 平移地图，识别完成前不发建造点击 |
| 已选择道路、轨道、地形工具 | 单指拖动 | 预览起点与终点；释放按工具语义提交 |
| 任意地图工具状态 | 双指平移 | 导航地图，不执行建造；结束后等待余留指释放 |
| 地图 | 双指捏合 | 围绕双指中心缩放，与平移独立 |
| 列表、订单等面板 | 单指滑动 | 滚动；排序/拖放使用明确入口或长按后拖动 |
| 图标、控件 | 长按 | 可读的帮助/上下文动作；避免与地图平移混用 |
| 建造中 | 可见的“取消” | 清理放置工具和预览 |
| 编辑框 | 单击 | 系统键盘、中文输入；完成/取消后恢复游戏焦点 |
| 精确地块选择 | 建造预览；可选精确模式 | 光标偏离手指、放大预览或相对移动后确认 |

地图与 UI 的手势应根据触摸开始时的目标锁定，由游戏线程判断 viewport、工具和窗口状态。低层识别器负责手指序列与几何；上下文路由负责平移、建造、帮助和列表动作。ArkUI 辅助控件与 XComponent 需要明确命中区，避免一次触摸同时触发辅助按钮和地图。

不需要用常驻全尺寸虚拟键盘承载所有快捷键。暂停、加速、拆除、订单删除等已有可点击入口；共享订单也有 Go To 菜单选项（`order_gui.cpp:1367,1464`）。取消工具可再点当前工具（`src/main_gui.cpp:70`），或关闭相应 picker（`window.cpp:3602`）。这些应保留并改善可发现性。

重点补齐缺少清楚按钮的语义：Shift 成本预估（`src/command.cpp:214`）、Ctrl 车站合并选择（`src/station_gui.cpp:2445`）及特定车辆/订单动作。优先提供“估价”“合并车站”等上下文操作；复杂功能可用明确的一次性 Ctrl/Shift 开关，操作完成、取消或失焦时自动清除。

本次保留现有可运行 PC 实现，仅新增评估与诊断产物。后续修改公共 GUI 代码时应记录必要性并覆盖 PC 回归；各端共享输入语义，布局按可用窗口尺寸与实际输入能力选择，不只按设备名字切换。

## 无键鼠验收矩阵

测试时移除键鼠与手写笔，禁止用 HDC 注入键盘事件完成用户步骤。记录型号、OS/API、ABI、显示/窗口像素尺寸、density、可用 vp、安全区、构建 Build ID、语言和输入法。平板横屏/竖屏/分屏、手机横屏/反向横屏、键盘弹出分别记录结果；未承诺完整竖屏游戏时需有明确且可操作的转向流程。

| 用例 | 必须观察的结果 |
| --- | --- |
| 冷启动、新建世界、中文改名 | 无外设即可操作；候选提交/取消、删除和光标位置正确 |
| 导航地图 | 单指/双指平移、慢速/快速捏合均可用；缩放中心稳定；工具状态不误建造 |
| 多指安全 | 两指先后抬起、长时间双指停留、第三指加入、Cancel/失焦后余留 MOVE/UP 均不产生点击或建造 |
| 建造与取消 | 道路/轨道、车站、车库、桥梁、拆除/地形等可完成；预览可读；取消不提交；估价和合并车站可达 |
| 运输闭环 | 购买车辆、设置至少两个站点订单、修改/删除订单、启动车辆，观察完成往返并有收入 |
| 列表/窗口 | 长列表可滚动；订单拖放可用；关闭/调整窗体可用；常用说明无需悬停 |
| 保存与加载 | 用系统中文输入命名，保存、退出、重启加载，车辆与订单仍在；资源选择流程可达 |
| 系统返回 | 优先收键盘/取消工具/关闭弹窗，最后进入正常退出流程 |
| 窗口变化 | 旋转、分屏、折叠形态变化、键盘展开/收起后界面可达、点击不偏移、手势不挂起 |
| 生命周期 | 锁屏、通知/切后台、恢复和系统进程回收分别测试；输入/音频状态正确，恢复策略明确 |
| 持续运行 | 固定存档和视角，分别测静止、地图平移、建造、大世界运行；记录帧间隔、输入延迟、内存、温升/耗电及音频 |

性能对比复用 `performance.md` 的采集方法，PC 的提交帧率不外推为手机流畅性；触屏连续地图移动会增加纹理上传，必须用目标硬件测量。先确定目标设备与代表存档，再制定持续运行预算。
